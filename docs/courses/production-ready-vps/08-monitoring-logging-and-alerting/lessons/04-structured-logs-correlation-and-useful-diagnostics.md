# 04 — Structured logs, correlation, and useful diagnostics

## Learning objectives

You can produce logs that help answer operational questions, correlate a request across the proxy and application, bound log growth, and investigate incidents without collecting unnecessary sensitive data.

## Logs are an event record, not a data dump

Logs explain discrete events: a process started, a request failed, a migration completed, or a dependency timed out. Prefer structured output such as JSON when the application and collection path support it. A useful event commonly includes:

| Field | Purpose |
|---|---|
| Timestamp | Correlation across systems; use UTC or an explicit offset and synchronize host time |
| Severity | Filtering and consistent alert/routing behavior |
| Service and environment | Identifies the producing component without relying on a free-form message |
| Release/version | Connects behavior to a deployment |
| Event name/message | Stable description of what happened |
| Request/correlation ID | Connects proxy and application events for one request |
| Duration and result | Supports diagnosis of slow or failed operations |
| Safe error class/code | Distinguishes failure type without dumping secrets or personal data |

Keep field names, severity semantics, timestamp format, and message meaning consistent. Do not log every successful low-value event at high volume. Use request-level success metrics for rates and reserve logs for evidence that changes an investigation or audit decision. Never record passwords, authentication tokens, session cookies, private keys, full payment details, database connection strings, or request bodies by default. Email addresses, IP addresses, user IDs, query parameters, and exception text can also be sensitive or identifying.

## Correlate without trusting arbitrary identifiers

Use a request ID generated by a trusted proxy or application boundary and propagate it through the request path. If a client can supply an ID, validate its length and characters or generate a new one; otherwise an attacker may inject log delimiters, confusing values, or huge fields. The proxy and app should agree on which header carries the ID. Avoid logging the full incoming header set.

Include release identity and component name so logs from a deployment can be distinguished. Synchronize clocks using the operating system's time service; time drift makes ordering across containers and hosts misleading. Include timezone or use UTC. Never use request IDs, user IDs, URLs with arbitrary parameters, or exception text as unbounded metric labels; logs can preserve richer values under access controls, but still need size limits and privacy review.

Use a stable event description and safe structured error type. Stack traces can help diagnose application defects, but restrict access and scrub secrets/identifiers before emitting them. If an exception includes raw user input or credentials, logging the entire exception can violate the privacy policy.

## Collect selected logs with Alloy

On Linux, Alloy can read selected records from the systemd journal with `loki.source.journal`, optionally process them with `loki.process`, and send them to Grafana Cloud Logs through `loki.write`. Filter at the source to the units needed for operations instead of forwarding the entire host journal by default. The Alloy service account needs permission to read the journal; Grafana's package guidance uses the `adm` and `systemd-journal` groups, which can expose more records than a single service. Review that privilege against the VPS's data and document it. Keep labels bounded, for example `service` and `environment`, and do not promote request IDs or user values into labels.

This is the shape of a journal-to-Cloud pipeline; replace the service host and tenant ID with values from the Grafana Cloud stack, and keep the token in a protected file readable only by Alloy and root:

```alloy
local.file "cloud_logs_token" {
  filename  = "/etc/alloy/secrets/grafana-cloud-logs-token"
  is_secret = true
}

loki.source.journal "web" {
  matches    = "_SYSTEMD_UNIT=nginx.service"
  labels     = {service = "nginx", environment = "production"}
  forward_to = [loki.write.cloud.receiver]
}

loki.write "cloud" {
  endpoint {
    url = "https://<your-loki-host>/loki/api/v1/push"

    basic_auth {
      username = "<your-loki-tenant-id>"
      password = local.file.cloud_logs_token.content
    }
  }
}
```

The token file must not be committed or copied into the Alloy configuration. Create a Grafana Cloud access-policy token with only the required `logs:write` scope. Check the Alloy service logs and Grafana Cloud Logs/Explore for fresh, expected records after reloading the configuration. Add parsing or redaction in Alloy only as defense in depth; prevent secrets from being emitted by the application in the first place.

Container stdout/stderr is not automatically part of the systemd journal. Inspect the Docker logging driver and choose one explicit path: configure the runtime to use journald, read a bounded and permissioned log file, or use Alloy's Docker source after a security review. Access to the Docker daemon socket grants powerful control over the host; do not mount it into Alloy just for convenience. Define retention and rotation for the chosen source. Avoid double rotation or duplicate collection, which can lose or multiply records.

Set maximum event size, volume limits where supported, local journal retention, remote retention, and a response to collector/destination failure. Do not assume Alloy buffers indefinitely during an Internet or Cloud outage. Test how its state, write queue, and the journal retention behave during a short interruption, without allowing telemetry to fill the VPS disk.

Centralized or remote log storage can preserve evidence if the VPS is lost, but it creates another privileged data store and potential cost. Encrypt transport, restrict access, and document where copies live and when they are deleted. A monitoring service's built-in retention default is not a policy.

## Make queries answer incidents

A useful first response can filter by service, severity, time range, release, and correlation ID. Test queries for common questions: What changed around the first failed probe? Which component emitted the timeout? Did errors begin at deployment or before it? How many restarts occurred? Can logs distinguish application failure from proxy or database failure?

Logs are not automatically a reliable audit record. If a security or compliance decision requires tamper resistance, identity attribution, or long retention, design a separate audit trail and verify its controls. Ordinary operational logs may be sampled, rotated, dropped, or mutable.
